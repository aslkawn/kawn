## Purpose and method

Purpose: an independent list of every behaviour in the studied application's space and sea domain, explained at technique level so a clean-room team can rebuild it, and a comparison against our existing notes (00 to 12). Domain: satellite positioning and orbit drawing, the ISS, satellite classes and icons, selection and follow, pass prediction and visibility maths, the celestial (sun and moon) ring, sun/moon/star rendering, launches and the rocket replay, vessels (AIS), and the submarine-cable layer's ties to the sea.

Method (enumeration was done before reading our notes): read the project README, known-issues note, data-source note, change log and the current-state note; read the whole satellite, launch, vessel and cable layer folders, the data helpers (class table, pass maths, orbit-path helpers), the celestial ring module, the server proxies for orbital elements, launch data and the AIS stream, the voice-action and external-tool catalogues, and the colocated tests' titles. ## 1. How satellite positions are computed, in plain words

**Inputs.** For each satellite the app holds one "element set": a short two-line text record published by CelesTrak (a US public service that republishes the US Space Force's tracking catalogue). It states: the moment it describes (its epoch), the shape of the orbit (how stretched, how tilted against the equator, where the tilt line points, where the closest point lies, where along the orbit the satellite was at the epoch), how many orbits per day it flies, and a small drag term that says how strongly the thin upper air slows it. The app also needs the current wall-clock time.

**Calculation.** A standard published model called SGP4 (Simplified General Perturbations, version 4; deep-space variant for orbits of 225 minutes or longer, such as GPS and geostationary) rolls the orbit forward from the epoch to "now". It is a fast formula, not a simulation: it includes the Earth's equatorial bulge, the average drag effect and, for high orbits, the Sun's and Moon's pull. It runs in the browser through a standard SGP4 library; no server computes positions.

**Outputs.** The model gives position and velocity in a non-rotating frame centred on the Earth. The app then turns the clock time into the Earth's rotation angle (Greenwich sidereal time) to find which spot on the rotating Earth is below the satellite, giving longitude, latitude and height above the reference ellipsoid. Height is kept in metres. Speed shown is the magnitude of the non-rotating-frame velocity, so it is the "orbital" speed (about 7.7 km/s for the ISS), not speed over the ground.

**Update rate.** The whole core fleet (about 840 satellites) is recomputed once a second, about 1.6 ms of work per pass. While a satellite is tracked the fleet pass speeds up to every 200 ms, and the tracked satellite alone is recomputed on every drawn frame (about 60 per second) with one shared clock reading, so dot, label, camera and speed readout cannot disagree. Elements themselves are refetched every 5 minutes by the client, but the server only goes upstream once per 6 hours per group, so most refetches are cache hits.

**Accuracy limits (general knowledge, not measured in the app).** A fresh element set is good to about a kilometre at its epoch. Error grows with age, typically a few kilometres per day for low orbits because drag changes with solar activity and the model only averages it, and much more after a manoeuvre such as an ISS reboost or a Starlink orbit raise. For a naked-eye pass, a day-old ISS element set is usually right to seconds; a week-old set can be off by tens of seconds to minutes. Geostationary and GPS orbits are far more stable. The app never checks element age: it does not warn when an element set is old, only when the proxy says it served a stale copy because CelesTrak was down. Other simplifications: the observer is at sea level, the Earth is a sphere of 6,371 km for the shadow test, there is no atmospheric refraction, and brightness and weather are ignored.

**Orbit ring (path).** To draw an orbit, the app computes 181 points spaced evenly in time across one orbital period (period from the element set's orbits-per-day), using one frozen Earth angle for all of them so the loop closes instead of drifting west by about 24 degrees. The ring is therefore a 3D orbit shape, not a ground track. It is baked once; every second the whole ring is rigidly rotated about the polar axis by the Earth's rotation since the bake, which keeps the ring locked under the live dot with no recalculation and no flicker. A true ground track (the line traced on the surface) is not drawn anywhere.

## 3. Gaps found, with the missing behaviour written out

**G-01. Orbit-computation mechanism and accuracy (SAT-04, SAT-13).** Fill 03 s6 with section 1 above: inputs (element set with epoch, shape, tilt, orbits per day, drag term), SGP4/SDP4 model, outputs (inertial position and velocity, converted to longitude/latitude/height using Earth-rotation angle), tiers of update rate, ring built over one period with a frozen Earth angle then rigidly rotated, and the limits (no element-age check, error grows with age, manoeuvres not modelled, sea-level observer, no refraction).

**G-02. Fleet cadence while tracking and hidden-points skip (SAT-05).** While any satellite is tracked, the fleet pass runs every 200 ms instead of 1 s; while points are hidden (Space Missions) no fleet pass runs. Add to 03 s6 Cadence.

**G-03. Ring styling and absence of ground track (SAT-15, SAT-41).** Rings: tracked yellow, ISS red; 60 percent alpha in front of the Earth, 35 percent where hidden behind it; 2 px (2.5 px ISS); not pickable. No ground track and no coverage footprint exist; the ring is the 3D orbit.

**G-04. No time control (SAT-40).** Satellites and passes always use the current clock; add a note so Kawn plans a time scrubber (SGP4 can compute any time, the engine's own clock is unused).

**G-05. Sun, moon, stars, day/night (SAT-36, SAT-39).** State plainly: only two celestial bodies, Sun and Moon, exist in the ring (no planets, see correction C-01); directions come from the engine's built-in low-precision model; the 3D scene has no custom sky, stars or terminator; the ring is a camera-plane direction, not an observer sky chart.

**G-06. Approximate orbit heuristics (SEA-08).** As written in the table: altitude by orbit name (550 / 20,200 / 35,786 km), launch azimuth rules, 12 or 8 degree downrange offset, 97 points; real inclination, node and phase are ignored, so the estimate is a labelled illustration only.

**G-07. Launch/satellite match rules (SEA-07).** Scoring and rejection as described; threshold 12; launch-year check on the international designator; search order core catalogue then full active group.

**G-08. Replay compression and insertion time (SEA-10, SEA-15).** Insertion offset from timeline events; compression 12 s per 600 s of real ascent, clamped 8 to 36 s; fallback speed 9,000 m/s with a 180 s floor.

**G-09. AIS sentinel and static-merge behaviour (SEA-25, SEA-26).** Add to 03 s5: "not available" codes are blanked rather than shown as 102.3 knots or 360 degrees; static reports merge into live rows by MMSI so names arrive late and vessels show "MMSI n" first.

**G-10. Newest-first truncation and ignored area (SEA-27, SEA-29).** The bundled server returns rows newest first up to the cap and ignores the centre/radius the client sends. For Kawn: filter by bounding box on the server (Gulf), and when the world exceeds the cap sort by distance to the view.

**G-11. No vessel motion between polls, no ports, no cable-ship tie (SEA-36, SEA-42, SEA-50).** State these as absences so they become Kawn additions: dead reckoning from speed and course between reports; port and anchorage overlays with dwell and arrival counts; cable corridors with ship-in-corridor alerts.

**G-12. Satellite lookup by voice picks the first substring match (SAT-22).** Differs from the pass lookup, which refuses ambiguity. Kawn should use the ambiguity-safe rule everywhere.

**G-13. Show-points / show-orbits parameters (SAT-16).** No user control exists; they are internal switches used by Space Missions. Kawn should expose per-layer toggles for dots and orbit rings.

## 4. Corrections to existing docs

- C-01. Doc 01 (Display table, "Celestial" row): says "sun/moon/planet direction markers". Only Sun and Moon markers exist; there are no planets.
- C-02. Doc 03 s7 (Honesty labels): "Reconstructed ascent is one continuous 128-sample curve". The curve is built with 512 intervals (513 points); the last 52 points are then replaced by a smooth join into the orbit.
- C-03. Doc 03 s6 (Cadence): "Positions recalculated every 1 s" is incomplete: 1 s idle, 200 ms while a satellite is tracked, per-frame for the tracked one only.
- C-04. Doc 03 s5 (Viewport / view-area query): reads as if the server narrows results. The built-in server ignores centre and radius; the narrowing is only a request, not a filter.
- C-05. Doc 03 s6 (Orbit rings): "Optional rings/paths" implies a user choice; no UI exists for it (see G-13).
- C-06. Doc 03 s7 (Replay): the ascent duration range is stated without its derivation (G-08); the pre-countdown tile-settle wait is a separate 5 s phase shown as "preparing launch site", not part of the T-10 count.
